Shipped 2026-07-20 — the .dop arc

  • .dop files were being INVENTED, and a day's colour work landed where PhotoLab cannot read it SHIPPED 763e5d5 + cd7c059, user-verified live. Culling a day with the .xmp channel switched off wrote colour to the .dop, and sidecarlib.ensure_dop created one when none existed. One afternoon left 647 SpeciesViewer-authored .dop files (empty Base, schema "19.5") holding 44 Green + 3 Yellow in a form PhotoLab misreads. The skeleton's own comment had called this “the one unverified assumption in this path”; it was later verified and is false — PhotoLab assigns each RAW a random v4 UUID in its own catalog and matches items by it, so a recipe we author is taken as a virtual copy; the UUIDs cannot be computed and the format has no master/virtual flag.

    Fixes. (1) ensure_dop never creates — it returns an existing recipe or none, and the skeleton is deleted, not disabled, since a dormant one invites a retry. (2) Write both channels — colour, rating and crop go to the .xmp always and to the .dop whenever PhotoLab authored one. The old 2×2 switch was a false choice: PhotoLab ignores the .xmp when its metadata sync is off, Lightroom ignores the .dop always, and neither reads the other's file under any setting — so writing both cannot conflict and is the only way they stay in step. Changed in the single gate (utils/sidecar_policy), not at the nine call sites.

    The Sidecar Behaviour dialog lost its four checkboxes — switches that decide nothing are worse than none — and explains the behaviour instead, with the PhotoLab advice. The supported direction is: PhotoLab authors, we edit. Verified live: a day went 36 files (ORF+XMP) → 54 (ORF+DOP+XMP) after Ctrl-A → write sidecars, and our colour then merged into a genuine recipe (Software = "DxO PhotoLab 9.8", full Base, real CafId). Recovery for files already invented: tools/svr_dop_colour_scan.py is read-only, reports what each holds, and tells ours from PhotoLab's (our Software stamp and an empty Base) so real recipes are never swept up with them.

  • The DxO options are one subject, and now one menu SHIPPED 99e5d61 — the PhotoLab path was a lone field at the bottom of Global Settings while Denoise and Sidecar Behaviour sat loose in the Settings menu. Now File ▸ Settings ▸ Interfaces to Lightroom and PhotoLab: PhotoLab Location… (the path moved there; [Global] dxo_path unchanged, and it now says at once whether the path is real — a PhotoLab upgrade renames the folder 9→10, which otherwise only surfaces later as a failure to open a picture), PhotoLab Denoise…, Sidecar Behaviour….
  • After an ingest, offer PhotoLab — and say why SHIPPED 99e5d61 + cd7c059 — a freshly read day has no .dop, and we no longer invent them, so colour and crop set before PhotoLab has seen the day live in the .xmp alone. It hands PhotoLab a RAW file, not a folder: _last_dest is the days-location parent (“…/2026 Zomer”), never the day itself, and PhotoLab is single-instance so a folder argument merely raised its existing window on the SD card it already had open. 2. Albums CORE + RETIRE COMPLETE RE-ARCHITECTED

An album is now a LIVE QUERY over the master by its date range, not a copied-out set of per-day CSV snapshots — the single biggest change in this chapter and the thing that dissolves most of the bug list below.

Album re-architecture (S0–S6) SHIPPED. An album used to be per-day CSV snapshots that svv2 Extract Days copied out of the master; they went stale the instant the master changed — the root of every GPS / crop / rating / qualifier staleness bug here, and why the 9 albums carried ~33% ghost pictures. An album is now a query: fromdate ≤ DateTimeOriginal ≤ todate over the master (MasterDB.pictures_in_daterange + batch/album_source.py), exactly the way the Master Species Viewer filters by species — so there is one copy of the truth and the stale-copy class is gone.

  • Read side — the overview (day list + Pictures/JPEG/GPS counts), the day viewer (cards, crop marks, captions), and the map all read the master directly. The map seeds each picture's placed GPS from the master mirror, so Helgoland (a camera with no receiver) now plots every picture.
  • Publish side — svv3 (blog), svv4 (website) and svv6 (make-clickable) all load per day from the master; svv2 Extract Days is retired (menu + every pipeline) and nothing writes metadata/review/ any more. Build Website now opens the species overview in the browser on finish, like Write Blog does for the blog index.
  • One master card menu — the album day viewer converged onto the Master Species Viewer's full surface (sex/age/plumage · pin best-JPG · delete-JPG · move-to-species · add renders · delete) via a shared gui/master_ops.py; the two viewers' duplicate copies are gone. Album edits (rating / colour / qualifier) mirror into the master DB, so the blog + website publish the right form (a picture marked imm. or ♂♀ br. now shows it).
  • Authoring gated to BigBoy — Create / Find-Trips / Import / Retire need the full master (readonly_locked); a SmallBoy can view + publish but not design.

This makes the old “re-extract the 9 stale albums” chore moot — there is no extract, and nothing to go stale.

The rest of the arc remains shipped and live: create → migrate & upload blogs → build website → make blogs clickable → add to master. Retire-a-trip-to-a-virtual-trip runs the entire chain from one confirm (verified end-to-end on BigBoy/Braakman), published under /trips/<name>/. Blog re-render (svv6 “make clickable”) and the per-day blog editor are done.

  • Geotag the master from the virtual-trip map SHIPPED — the map was flatly read-only because an album's files are the master's — which also made it the best surface we have for fixing the master's missing coordinates. Geotagging is now let through, and only geotagging: rating, colour, crop and delete stay refused, and the permission is gated on the machine's existing master write policy, so a read-only master still gets the view-only map. Two rules hold it honest. Fill, never overwrite: you can place a picture that has no coordinate, but you cannot drag a bubble to move pictures whose coordinates the camera recorded. And the map says what it does — where it read “· view only” it now reads “· placing writes to the master”.
    To see where the work is, each day now shows a No GPS count; double-click it to open that day's map. Sri Lanka: 285 of 2060 pictures, with two days consisting of nothing but those — which is precisely why they auto-titled “onbekend”.
  • GPS provenance — telling our coordinates from the camera's SHIPPED — needed before any batch can seed coordinates from a place name, because a seeded picture has GPS and would otherwise be frozen: moving it is exactly what the map forbids. The idea of marking a derived coordinate by making it less precise (whole arcseconds) was tested against the master and 791 of 41,246 GPS'd pictures (1.9%) already look like that — Galapagos 2015 repeating one coordinate across many photos, a South Africa shot at a suspiciously round position. The instinct was right that something is there, but as a permission signal it fails, and it rides on a number that any tool may reformat. So the idea was split into its two true jobs:
    Permission now lives in GPSProcessingMethod, the field whose actual purpose is recording how a fix was obtained. Blank means the camera measured it and we do not touch it; “manual” means a person placed it, so it may be moved and refined.
    Precision is about telling the truth: a place-name look-up is accurate to tens of metres, so its coordinate is rounded to match — and it visibly reads as approximate (47.00" beside a camera's 46.52"), which is the cue that it still wants attention. It never decides what you are allowed to do.
    The map's rule therefore sharpens from “fill, never overwrite” to “never overwrite what we did not put there ourselves”.
  • Get GPS from location SHIPPED — the mirror of Get location, sitting right under it in the same menu. That one turns a coordinate into a place name; this turns the place name a picture already carries into a coordinate. It is the answer for the older trips, whose camera had no GPS but whose files say “Helgoland”.
    All 93 pictures of a day share one written place, so it is one look-up, not 93. Nothing is written until you have seen it: a review table shows the written place, what OpenStreetMap found, the coordinate and how many pictures would get it — untick anything you don't trust. The result is deliberately rough (~30 m) and marked as placed by hand, so the next step is to open the day's map and drag the clusters onto the right cliffs. Seed, then refine.
  • The Helgoland bug hunt SHIPPED — running the feature for real turned up six defects, and they were all the same shape: one truth on disk (the picture's sidecar) and several things reading a stale copy of it. A moved picture snapped back when the map was re-opened (the data was never lost — the map was reading its own out-of-date list). The day table said 93 pictures had no GPS when the true answer was 1. “Map whole trip” opened on an empty world map while the day map showed 92 of them on the island. Underneath, the metadata cache had been poisoned: a geotag writes a coordinate, a method and a place name, but only the place name was recorded — so the cache went on insisting the coordinate wasn't there. And an unexplained three-second delay turned out to be the cache being kept inside Dropbox, where the sync client locked it just as we saved, so the save was lost and that folder re-read every file from scratch, every time. It now lives with all the other caches, outside the synced folder. Placing pictures also got far quicker: dragging 62 of them used to launch the metadata tool 124 times, and now does it twice.
  • A placed JPG-only picture wouldn't stay placed SHIPPED — same shape as the bug hunt above, one more stale copy. On the Tucson 2023 map two birds kept coming back to the “without GPS” tray on every re-open, and the trip's no-GPS count never dropped, even though the coordinate had in fact been written to the file and was sitting there on disk. The catch: those two were JPG-only pictures — a phone or a friend's camera, no RAW and no separate sidecar — so their GPS lives inside the JPG itself. Both things that re-read a placed coordinate only ever looked at the .xmp sidecar and never at the JPG, so a JPG-only picture was invisible to them. They now fall back to the JPG when there's no sidecar. Nothing was ever lost — the placement had always saved; only the reading-back was blind. Confirmed live: the two caracaras drop out of the tray and the day count goes 2 → 0.
  • Find a place by name SHIPPED — we had OpenStreetMap look-up in one direction only (coordinates → place name). How it works now

  • A picture is a “blog extra” when its subject carries a marker keyword (landscape / landschap → isBlogExtra). It is deliberately exempted from species resolution (so it doesn't warn as an unknown species), renders in the day blog as a card with no taxon, and is excluded from species groups.
  • It is SKIPPED when freezing to the master — both its picture record and its file records (sv6Freeze), logging “N blog-extra (landscape) pictures excluded”.

Why it is architectural, not a small feature

The master's whole organising principle is the species: the on-disk tree is species folders (TargetPath from the taxonomy chain), and species is the key for the MasterDB index, the counters, “move to species”, the per-species website pages, the best-JPG/rating pick, and the audit/heal tooling. A landscape has no taxon, so there is no answer today to “where does it live and how is it found.”

The real problem (and the reason to do this)

Nothing is lost today — verified: neither delete path touches landscape originals (retire removes the trip's metadata repo, not the picture files; the delete tool only removes a file whose UPN is in the master, and a landscape never is). But landscapes have no path into the master at all, so they are never backed up. After a retire, a landscape survives only as a loose file in the picture root — no master copy, no trip index, and permanently un-cleanable (the cleanup tool reports it “keep — not in master” forever). They accumulate as un-backed-up orphans, one disk failure or one manual cleanup away from being gone.

Direction (user, 2026-07-12): a topics/ branch beside biota/

Add a sibling top-level branch for non-biota subjects — e.g. topics/landscape/<year>/. The organising key stops being species and becomes subject, which resolves either down the biota chain (taxonomy → species) or down a topics chain (topic → leaf/year). TargetPath is already built from a chain, so a topics chain just yields a different root — it gives landscapes a real home, a backup path into the master, and a website home without special-casing them everywhere.

The record is fully reconstructible from disk even for an already-retired trip: subject + GPS/location from the .xmp, rating + colour from the .dop, date/camera/EXIF from the RAW.

⚠ The trap: a scan that reads only the .xmp finds the landscapes but silently loses every rating and colour label — those live in the .dop, not the XMP. Get this right up front.

Open design questions

  • Indexing — MasterDB and the CSV schema assume a species per picture; the generalisation is subject = species OR topic leaf, or species-less records ripple into every species-keyed query, counter, audit and the “move to species” tool.
  • Website — stay blog-only (stored purely for safekeeping) or earn a home (topic pages / a per-year landscape gallery)? Storage and publication are separable.
  • “Best” without a species — the rating/best-JPG pick groups by species; group by topic leaf (year/place), or not at all?
  • Migration — every trip committed so far excluded its landscapes; a backfill would re-ingest them from the picture root.
  • Declaring a topic — today the marker is a hardcoded keyword set; a topics branch needs a small registry (topic → leaf rule) so planes/F16 isn't a code change.

Order of work

The scan cannot go first — there is no TargetPath until a topic has a rule. (1) Topic registry — declarative topic → leaf rule. (2) Scan → dry-run report — walk the picture root with the parallel EXIF reader, listing every topic picture and what was reconstructed from RAW + .xmp + .dop. (3) Reviewed ingest into topics/…, with backup — dry-run → review → explicit apply, never an auto-fix.

13. Web viewer — searchable species pages SHIPPED

The published website's species pages are static HTML with no server behind them — so a visitor wanting "any duck" had to scroll a page listing every species in a family, or every species there is. A small client-side search fixes that without needing one: type a (partial) string and matching cards stay, the rest hide, with a live "N of M species" count. Typing duck narrows a family listing to just the ducks; typing a full scientific name works exactly the same way — it is one filter, not two modes.

  • Runs entirely on the client SHIPPED — ~10 lines of vanilla JavaScript, no server round-trip, no build step: every species <div> already carries its scientific, English and Dutch names as text, so the filter is a single textContent.toLowerCase() match against all three at once, toggling display. The site already runs inline scripts, so this added no CSP or hosting concern.
  • Lives on every listing page, not just one SHIPPED — the big all-biota summary page and every taxon/family page (Vogels, Zoogdieren, Insecten…) both carry it, in Dutch and English (4 templates total). Wording adapts to what the page actually lists: the summary keeps "soort"/"species", a family page reads "Zoek op naam…"/"Search by name…" with a unit-less counter, since a family page can be listing orders rather than species.
  • Hides itself where it isn't needed SHIPPED — a page with fewer than 12 cards gets no search box at all; a short list doesn't need filtering, so the box only earns its place once scrolling actually gets old.

Publishing has two real gotchas, both cost a rebuild cycle to learn. The summary page is rendered only by the site-build step (sv5BuildWebsite for a trip, svv4BuildWebsite for an album) — the "make blogs clickable" step does not regenerate it, so republishing the blog alone never picks up a search-box change. And a locally-rendered page isn't live until Publish/Commit runs — the upload only skips files whose content hasn't changed (by CRC), so a changed template still needs an actual publish pass, not just a rebuild. Verified live across Costa Rica, Marokko, Helgoland and Greece.

14. Desktop Biota Browser — the website, offline, with everything in it SHIPPED

The public website necessarily shows a curated slice: one best picture per species (per age/sex/plumage group), and nothing at all once you're offline. The Biota Browser is the desktop answer to both limits — a taxonomic browser styled to look like the website, that reads the master (or a trip, or an album) directly off disk, so it works with no internet and can show every picture the collection actually holds, RAW files included. It doubles as a showcase of what a Qt application can look like once it stops looking like a default Qt application.

  • One dialog, three scopes SHIPPED — Master ▸ Biota Browser… is the full, editable collection; Trip ▸ Biota Browser… and Album ▸ Biota Browser… browse the same way over a trip's own repository or an album's live date-range window, read-only (editing stays in the authorized panels). A trip repo is master-shaped on disk, so it gets its own small SQLite cache rather than sharing one — never touching, and never risking, the real master's cache.
  • Two ways to arrive at a species SHIPPED — a tree mode walks Kingdom → … → Species with a rank filter, a search box that works at whatever level you're standing on, a left rank rail to jump straight to an ancestor, and a back-history button; an All Species flat index lists every species in the collection (2248 on the real master) behind the same live search, so "start typing" always works whether or not you know the taxonomy.
  • The species page mirrors the website, on purpose SHIPPED — click a species and you land on a pretty, read-only page: hero photo shown at its own natural aspect (no forced crop into a banner), a names table, photos grouped by age/sex/ plumage exactly like the site groups them, a distribution map, and a sibling/order sidebar for browsing sideways. A ⚙ Tech panel button swaps to the same editable picture grid used everywhere else in the app (rating, colour, qualifier, crop, move-to-species, delete) — the pretty page for looking, the tech panel for working.
  • "Show all files" is the whole point of doing this locally SHIPPED — the website only ever shows the curated best JPG per group. Toggling this on reveals every RAW-only frame too, marked with a small # where a JPG exists alongside it — the full contents of the master, not the subset that ever got uploaded. Only possible because the browser reads the database directly instead of a rendered page.
  • Styled like the website, not like a generic Qt dialog SHIPPED — every photo sits in the site's own olive mat (#6d8764), and the whole dialog runs the same ink/line palette as the Trip lifecycle board rather than bare-Qt grey. It was the first place this palette got used consistently enough to notice it was a real design language rather than one-off styling — the seed for the app-wide theme in ch. 15.
  • A map that goes further than the site's SHIPPED — a species' distribution map, opened from a trip or album scope, plots the full master range in the usual colour and overlays that scope's own pictures in amber with a legend chip, so you can see at a glance which of a species' worldwide sightings are the ones from this trip.

Live-confirmed on the real master (2782 taxon nodes, 74k+ pictures); the Trip and Album scopes were headless-verified before their first live pass, matching the standard this app holds every new grid to before calling it done.

This chapter grew out of the Biota Browser above: building it, the Trip lifecycle board and the Species panel each independently invented a near-identical olive/ink palette, copy-pasted into each file by hand. That was the first sign a real design language already existed by accident — it just needed centralizing into one theme the whole app could share, including a proper light/dark switch. 16. Species Name Display SHIPPED

The species name shown under each picture is a display profile: an ordered list of the languages to render (Dutch / English / Scientific), de-duplicated so a name is never shown twice and fallback-filled so a card is never nameless. One resolver (utils/name_profile.py) serves every viewer — name_lines() for grid cards (the profile's languages only) and all_names_ordered() for the detail surfaces (all three names, the profile only choosing which leads). The scientific name remains the stable identity everywhere (paths, keys, matching); this governs display only, never the website output or species editing.

  • Eight profiles, one default. EN/NL (default), NL/EN, NL/EN/Sci, EN/NL/Sci, EN/Sci, NL/Sci, Sci/EN, Sci/NL. The former plain “Scientific only” is retired and normalises to Sci/EN. Chosen in Global Settings, the new Species Settings ▸ Preferred name display row (kept separate from the correction “name type”), or per trip/virttrip; a viewer's own combo is a per-session override. Precedence: per-view combo → per-trip → global default. Every dropdown that offers them lists them A–Z on the label — one profile_keys() sort serves all seven combos, and each selects by key, so no stored setting shifts when the list grows.
  • Every surface follows it. Trip / Master / Album Species Viewers, the culling “Species Image Preview”, the large image viewer, and the Biota Browser (tree cards, all-species index, species page) all read the same profile. Grid cards show up to three deduped lines with the scientific one italic; the qualifier (♂/♀, juv, br.) rides the primary line, since it is a property of the photograph.
  • Culling resolves names locally. A just-culled picture carries only the camera-stage subject. The same local species collection that yields the scientific name also holds the Dutch/English names (sc.sc_dict[sci]), so the culling grid resolves the full {NL, EN, Sci} triple and applies the profile — cached, no network.
  • Detail surfaces show all three. The large image viewer and the Biota species page lead with the profile's primary name and list the other two beneath, so the identity is always fully visible; the full triple also appears in the species page's Names & Classification table.
  • Names lift out as plain text SHIPPED — for captioning a printed photobook, the names have to leave the app carrying nothing but their characters. One module (gui/name_copy.py) owns this, with a single invariant: it only ever puts text/plain on the clipboard — no font, size or colour rides along. Each name copies individually (Dutch, English, scientific), plus “all names” (·-joined) and “all names, one per line”. Two shapes, because names sit on two kinds of surface: a widget that is a name becomes mouse-selectable and right-clickable (the species page — title, subtitle, and every cell of the Names & Classification table); a widget that carries a name but owns its clicks gets the right-click menu only (the Biota Browser's taxon cards and the sibling/orders sidebar rows — a selectable label there would swallow the mouse press and break click-to-open). The cards are one widget shared by the tree, the flat all-species index and the search results, so all three views and all three scopes get it at once. A taxon with only a Latin name offers that one entry and no “all names”; a nameless node shows no menu.
  • Biota grid legibility. Long taxon names auto-shrink to fit (down a few px, then up to three lines) with reserved height so nothing clips; higher taxa keep “vernacular + scientific” while species follow the profile; grid cells are top-aligned so a tall neighbour can't stretch a card's photo frame and a short row can't balloon to fill the window.
