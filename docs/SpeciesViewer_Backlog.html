    Done

    • Tracklog geotag (GPX import) SHIPPED — live-tested 16 August 2026, both entry points. A GPX/OM-1-log tracklog is matched to pictures by timestamp and fills in whatever's missing: GPS for a day the camera's GPS wasn't enabled at all, and/or altitude (which the camera never records even when GPS was on) via a 2×SD/±5min-window cleaned rolling average. This was the last piece of the old GPS / data-integrity umbrella — the rest shipped earlier as Get GPS from location, Get location, and Refresh Master Database.

      Two entry points, one dialog, one engine underneath: Master ▸ Maintain Master Database ▸ Geotag from Tracklog… (whole master, by date range) and a Geotag from tracklog… button on the Read-a-card dialog (Days/Trips/Unfiled all share that one dialog class), scoped to just the pictures that read just produced — useful before a day even reaches a trip or the master.

      Fixed 16 August 2026: the Read-Card "Geotag from tracklog…" button used to become clickable right when the copy phase finished, but if "Add location names" was also ticked, a few more seconds of geocoding followed behind their own modal progress dialog — a click during that window looked swallowed (not a crash, just bad timing; both write GPS-related fields into the same .xmp). The button now stays disabled until the whole read, geocode included, is truly done, and the misleading early "✅ Card read complete." log line (printed before the geocode step had even started) was dropped in favour of the real "Done" once everything has finished.

      Also fixed 16 August 2026: re-running the geotag over pictures it had already geotagged kept re-proposing the same altitude, forcing a needless re-confirm — a photo's current altitude is now compared to the proposal with a tolerance (5% relative / 0.5 m absolute) and skipped when it's already close enough. The empty-result message also used to blame everything on "nothing matched within the 15-minute cutoff" even when the real reason was a whole day outside the tracklog's date coverage, or pictures that were already geotagged — it now names the real reason (or a mix of reasons) instead of guessing.

      Shipped 16 August 2026 — auto-discovery + camera-clock auto-detection: the camera's UTC offset (needed to line a photo's local clock time up with the tracklog's UTC timestamps) used to be typed by hand or guessed from the tracklog device's own header — both assume the camera's clock/timezone setting is correct, which is easy to forget after traveling. It's now auto-detected by correlation search against the track itself (coarse 15-minute sweep, then a fine pass that also catches ordinary clock drift, not just a wrong timezone) — never a guess, a day it isn't confident about is simply skipped and logged. Works for both a Read's automatic pass and the manual dialog's offset field (still editable/overridable by hand).

      On top of that: a "Geotag from each day's tracklog…" checkbox on the Read dialog (ticked by default once a GPS-logs root folder is configured in Settings ▸ Repositories) silently fills GPS/altitude per day from <root>/<year>/<yyyymmdd>.log (or .gpx), on its own thread so it never blocks the dialog. It runs before "Add location names", so a picture that gets GPS from the tracklog also gets a place name in the same Read. And a standalone 🛰️ "Geotag from tracklog…" row action (icon + right-click menu) on the Unfiled and Days panels runs the same logic against an already-read day, independent of a card being present — opens the review dialog pre-loaded with that day's auto-detected log.

    4. Trip-to-Master Pipeline

    Done

    • Export / import a trip SHIPPED — move a trip between machines as a unit, as a small ZIP. Came up while deciding what should happen when the master is not reachable: the answer there is "that is an error", which only holds if there is a proper way to carry work from one machine to the other. What travels is what is hard to recreate (the trip's identity) or easy to forget (its species list, lifer baseline, hand-verified translations) — the pictures themselves move separately, by an ordinary file copy. Bringing work back the other way uses exactly the same export and import, so there is no separate "return" behaviour to trust.
    • A species is learned once, and then known everywhere SHIPPED — naming a species that was not yet in your list means a lookup on the internet. That lookup used to be thrown away by the species editor, saved to whichever list happened to be in front of the culling viewer, and only reached the master when you ran Publish Species Names by hand — so the same species was looked up again in the next trip and again on the other machine. A newly recognised species is now saved the moment you commit it, to the shared master list and the trip's own copy, and the next step in the pipeline already knows it. It is written by appending rather than rewriting the whole 2 MB list per species, which also spares Dropbox. If the master cannot be reached you are told, and nothing is lost — reconnect and it saves. Edit Species List is now a single entry (it was one per trip and one per master, and which one you opened decided who saw the correction). This also retires the planned GBIF lookup disk-cache — there is nothing left to re-look-up. Carrying a change made on the laptop into the master still needs a merge: Publish Species Names does that, and is now a reconciliation step rather than the only way the master ever learned anything.
    • The new-species count now stays true, whatever you merge next SHIPPED — Count Species tells you which species on a trip were new to you. It used to answer that by asking whether the species was in the master right now, which only worked as long as you read the report before merging the trip: afterwards its own species were in the master and every new species silently stopped being new. Nothing recorded what the answer had been. A trip's new species are now judged against everything the master has a picture of from before the trip's start date, worked out afresh on every run. It cannot be thrown off by merging this trip, nor by merging an older trip afterwards — a species first photographed in March counts as known on a May trip even if the March trip only reaches the master in July, which is exactly the case that produced a wrong count (48 instead of 47 on Greece) before this landed. The report names the rule it used, says how much of the trip it covers, and a day that was never summarized is named rather than quietly contributing nothing.
    • Landscapes are no longer mistaken for species SHIPPED — landscape/topic entries are stored looking exactly like species (2026, filed under topics/landscape/) and reach the counting code through the day summaries. They were only being kept out of the report by accident, and sat in the species lists behind it. They are now discarded as the summaries are read, and the report states how many it ignored.
    • The trip's species verdict now outlives the trip SHIPPED — Merge Pictures into Master starts by counting species and storing the result in the master: the full report, the species list it was judged against, and a row in admin/trip_species_summary.csv (species seen, new species, dates). It runs first because that is the last moment the master is still free of the trip, and it goes into the master because the trip itself does not survive — retiring a trip deletes its whole repository, and resetting one clears the day summaries the report is built from. "How many new species did that trip give me?" is now a question you can still answer years later, for every trip, without opening a single text file. Retire Trip warns when a trip is about to be deleted with no archived count, since that number cannot be recovered afterwards.
