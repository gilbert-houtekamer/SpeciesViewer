4. Trip-to-Master Pipeline

Done

  • Export / import a trip SHIPPED — move a trip between machines as a unit, as a small ZIP. Came up while deciding what should happen when the master is not reachable: the answer there is "that is an error", which only holds if there is a proper way to carry work from one machine to the other. What travels is what is hard to recreate (the trip's identity) or easy to forget (its species list, lifer baseline, hand-verified translations) — the pictures themselves move separately, by an ordinary file copy. Bringing work back the other way uses exactly the same export and import, so there is no separate "return" behaviour to trust.
  • A species is learned once, and then known everywhere SHIPPED — naming a species that was not yet in your list means a lookup on the internet. That lookup used to be thrown away by the species editor, saved to whichever list happened to be in front of the culling viewer, and only reached the master when you ran Publish Species Names by hand — so the same species was looked up again in the next trip and again on the other machine. A newly recognised species is now saved the moment you commit it, to the shared master list and the trip's own copy, and the next step in the pipeline already knows it. It is written by appending rather than rewriting the whole 2 MB list per species, which also spares Dropbox. If the master cannot be reached you are told, and nothing is lost — reconnect and it saves. Edit Species List is now a single entry (it was one per trip and one per master, and which one you opened decided who saw the correction). This also retires the planned GBIF lookup disk-cache — there is nothing left to re-look-up. Carrying a change made on the laptop into the master still needs a merge: Publish Species Names does that, and is now a reconciliation step rather than the only way the master ever learned anything.
  • The new-species count now stays true, whatever you merge next SHIPPED — Count Species tells you which species on a trip were new to you. It used to answer that by asking whether the species was in the master right now, which only worked as long as you read the report before merging the trip: afterwards its own species were in the master and every new species silently stopped being new. Nothing recorded what the answer had been. A trip's new species are now judged against everything the master has a picture of from before the trip's start date, worked out afresh on every run. It cannot be thrown off by merging this trip, nor by merging an older trip afterwards — a species first photographed in March counts as known on a May trip even if the March trip only reaches the master in July, which is exactly the case that produced a wrong count (48 instead of 47 on Greece) before this landed. The report names the rule it used, says how much of the trip it covers, and a day that was never summarized is named rather than quietly contributing nothing.
  • Landscapes are no longer mistaken for species SHIPPED — landscape/topic entries are stored looking exactly like species (2026, filed under topics/landscape/) and reach the counting code through the day summaries. They were only being kept out of the report by accident, and sat in the species lists behind it. They are now discarded as the summaries are read, and the report states how many it ignored.
  • The trip's species verdict now outlives the trip SHIPPED — Merge Pictures into Master starts by counting species and storing the result in the master: the full report, the species list it was judged against, and a row in admin/trip_species_summary.csv (species seen, new species, dates). It runs first because that is the last moment the master is still free of the trip, and it goes into the master because the trip itself does not survive — retiring a trip deletes its whole repository, and resetting one clears the day summaries the report is built from. "How many new species did that trip give me?" is now a question you can still answer years later, for every trip, without opening a single text file. Retire Trip warns when a trip is about to be deleted with no archived count, since that number cannot be recovered afterwards.

6. Taxonomy & Species PARKED (by design)

Not scheduled in the coming month (agreed 18 August 2026).

  • PARKED Sequence redesign — replace the “040 passeriformes” prefix with a Sequence float column (eBird TAXON_ORDER).
  • PARKED Auto-detect obscure flag — derive from the GBIF family, no extra API call.
  • PARKED Placeholder-species cleanup — the “? <name>” placeholders, coordinated cleanup.
  • PARKED Regional most-likely-birds (eBird).
  • PARKED Aliases for common names — the collection settled on its own names (IOC 10.5 with GBIF), and every list from outside disagrees somewhere. Comparing the two Brazil lists put a number on it: 86 of the 576 birds they share are named differently, and merging all four lists in the trip found 98. Three different problems wear the same face:
    • Spelling convention — Gray/Grey, Golden-Plover against Golden Plover. Mechanical, and the widest slice of the 98.
    • A genuinely different name for the same bird — Bank Swallow against Sand Martin, Mealy Amazon against Mealy Parrot. No rule derives one from the other; it has to be recorded.
    • A split or lump, where an old name does not mean one species any more. This is the dangerous one: an alias that guesses here silently files a photo under the wrong bird.
    The shape: a table of alias → scientific name, per language, with where it came from, living beside the other species metadata and learned as we go — when a list's name does not resolve but its scientific name does, that pairing is an alias worth offering to keep. Two rules hold it together: an alias points at a scientific name and never at another common name, so no chains form; and an alias that would be ambiguous after a split is refused rather than guessed — better to leave a name unresolved than to file it under the wrong species.
    Where it would pay: reading a tour operator's list, keywords typed in the field coming back through the pipeline, the waarneming.nl import, and searching for a species by a name you happen to remember. Until then the checklist and keyword steps do the narrow version of this — group by scientific name and keep our own spelling — which handles the first two kinds but knows nothing about splits.

17. Capture time & time zones

Not scheduled in the coming month (agreed 18 August 2026) — what shipped works and is measured; the storage decision below is deliberately left to sit.

A photo's capture time is really two facts: the instant (a point on the world's timeline, which decides where a tracklog says you were standing) and the local reading (the wall clock where you stood, which decides the day folder and what a caption says). A camera records the local reading; the instant is only recoverable if it also recorded its UTC offset. Treating these as one thing caused everything below.

To do

  • Decide how capture time is stored — the one open decision, and a big one, because it touches sidecars, data_files.csv, the website and the master. Today the instant is known but only lives in the sidecar; nothing downstream uses it. Three shapes were considered:
    • A — keep the camera's own reading and offset (what ships today): 10:30:55+01:00. Faithful, identical to the RAW, instant correct. The local reading is the camera's wall clock, which may not be the one you stood under.
    • B — normalise to true local time: 11:30:55+02:00. Same instant, displayed time matches reality. But it writes an inference into every picture, the sidecar then disagrees with the RAW forever (PhotoLab reads both), and with no tracklog for the day we would be guessing the zone again.
    • C — store the instant explicitly: a UTC column alongside the untouched local time. Nothing reinterpreted, both facts first-class, old rows simply empty. Costs a column and a pass through sv2ReadDirExif.
    Nothing forces this now: a zoned value cannot currently reach the CSVs (sv2 reads the EXIF group, which only comes from RAWs we never write), so the two parsers that would choke on a zone are safe until we deliberately send them one. Related and folded into the same decision: where a day's true zone lives (it may not be recoverable later, though the day-folder name already records its practical effect), and whether to add offline location→timezone lookup, which would settle the Nikon daylight-saving ambiguity for any picture with GPS. Full reasoning and the archive survey: docs/plans/timezone_plan.md.
  • Live-test the 🛰️ row action on the Days panel — built the same way as Unfiled's and never clicked. Small: open a Day, double-click the 🛰️ cell, confirm the review dialog opens on that day with its own log pre-loaded. The equivalent on Trip and Unfiled has been used live; Days is the last of the three.
  • Thinning the tracklog's points NOT WORTH IT NOW (measured 18 August 2026) — the old note proposed thinning the cleaned track to about one point every 5 minutes before correlation, on the grounds that altitude barely moves faster than that. Measured on the largest real log (4,341 points over 8.2 h, one every 6.8 s): parsing costs 10.6 ms, and the altitude cleaning 285 ms — 65 µs per point, and it scales linearly (verified to 69,456 points), so there is no hidden blow-up. The whole current log collection is four files and under a second in total. Nothing to win.

    There is also a flaw in the original idea: the same point list serves position lookup, not just altitude. Thinning before correlation would trade the sub-metre placement we now get for a saving nobody can feel. If a multi-day GPX ever makes a Read visibly slow, the right shape is to thin only the input to the altitude cleaning — that is where all the cost is — and keep full density for position. The trigger to revisit: roughly 70,000 points costs 4.4 s, so a multi-day phone log at 1 Hz (a few hundred thousand points) is where it starts to show.

    Worth noting the accuracy side cannot be settled from this trip's data: the pictures were taken from near-static positions (a whole day spans 150 m), so thinning changes almost nothing and the numbers wobble without trend. That is evidence it would not hurt this kind of shooting, not evidence that it is safe in general.
  • No bulk rewrite of existing timestamps DECIDED — all 75,050 master rows carry bare local time and not one carries a zone. Those values are correct as local readings. Recovering instants for the archive is a re-read of RAWs that can be done later, for whatever subset actually needs it.

Done

  • Tracklog geotagging now uses the camera's own clock offset SHIPPED (17 August 2026) — pictures geotagged from a tracklog could land kilometres from where they were taken, and nothing looked wrong, because both the right and the wrong coordinates were plausible places on the same island. Two independent causes. First, the OM-1 log's timestamps were read as local time when NMEA times are always UTC, which moved the whole track two hours; the log's own date is now used as well, so a track running past midnight UTC no longer stamps its later fixes a day early. Second — and the real problem — the camera's clock offset was searched for by correlating photo times against the track. On a short session that question has no answer: 202 pictures spanning 34 minutes against a 9½-hour track made 22 different offsets fit perfectly, so the result was decided by which one happened to be tried first. The camera had recorded the correct offset in every single file all along; it was simply being dropped when the XMP sidecar was written. The sidecar now carries it, and the search is gone — a day whose pictures don't state an offset is skipped with a message instead of guessed at.

    Measured on the same card and tracklog, counting only the pictures that actually got their GPS from the track: 8,585 m out before, 0.2 m after.
  • Camera-clock warning before a Read SHIPPED (17 August 2026) — after Scan days, the dialog compares the camera's own time zone against the day's tracklog (or, failing that, this computer) and says plainly when they disagree, before any copying starts. It also explains what is not affected: a stale zone does not spoil positions, because changing a camera's zone moves its clock and its recorded offset together, so UTC survives. What it does affect is the local time written into each picture — and the calendar day, which is why the Timezone offset field now fills itself in from the difference instead of being typed by hand each time.

18. Away from home — trip readiness

Everything in this chapter only bites when the nearest spare drive, second computer or willing helper is a few thousand kilometres away. None of it is a missing feature in the ordinary sense — the pipeline works — and that is exactly why these items never came up: at home each one has an easy way out. Raised and scoped 18 August 2026.

Two risks were considered and dismissed on the facts, so they are not on the list. Losing pictures: there are plenty of SD cards and no expectation of filling them, so the cards stay as the original copy for the whole trip — the RAWs are never the thing at risk. Working offline: each operation already gates on its own real dependency (publishing on SFTP, species lookup on GBIF, place names on Nominatim), so a hotel with no wifi degrades rather than breaks. What is genuinely exposed is the work: the culling decisions, species identifications, locations and blog text that exist only on the laptop.

How this chapter gets built — keep it simple. In ten years no memory card was ever lost; what was lost were CurrentPictures directories, when SpeciesViewer went rogue and deleted files. That is the honest risk record, and it points the opposite way from clever design: a sophisticated feature carries failure modes nobody saw coming, and the more carefully specified an item on this list becomes, the more expensive and the more dangerous it gets. So each item below is to be built as the smallest independent function that nothing else depends on — something the daily flow neither calls nor notices, that can be run, ignored or deleted without consequence. Where an item as written here is more elaborate than that, the write-up is the ambition, not the build order: cut it down first. Too good means we get nothing.

To do

  • Nothing watches free space, and a failed copy doesn't stop a Read SHIPPED (2026-08-19) — was the highest item here. No part of the program ever asked the operating system how much room was left. In the card copy, a failure on one file logged a warning and added one to a counter; the dialog then reported its ordinary “Copied N, skipped M, failed K” line, in the same tone whether K was zero or eight hundred. A laptop drive that filled up in week three therefore produced a Read that looked like every other Read, with a number in the middle of a sentence as the only sign.

    What was built. A free-space question is now asked before the copying starts, at the one moment the answer can be exact: the card read works in two phases, and by the end of the first one the program knows precisely which files it is going to write and how many bytes that is. If they do not fit — with a gigabyte of working room left over for sidecars, caches and simply not running the machine to zero — the read stops there and says so in plain numbers: needs 42.3 GB, only 11.1 GB free, nothing was copied. Nothing is half-done and the card is untouched. What the first phase already worked out is still saved, so once room has been freed the re-read picks up quickly and skips whatever did get copied.

    The second half is about tone. A read that lost pictures no longer ends on a green Done. It ends on a warning that counts the losses, names the first few files, and says the obvious useful thing — run the Read again, what already arrived will be skipped. This mattered more than it sounds: the closing line is written by whichever step finishes last, and when place-name lookup ran after the copy it used to report its own clean success over the top of a failed copy. All the endings now share one marker, so that cannot happen.

    One judgement worth recording: a single unreadable file does not abort the read. It finishes, copies everything it can, and reports loudly. A bad sector on one frame should not end a two-thousand-picture import. Only the up-front space check refuses outright, and it refuses before anything has been written.

    STILL OPEN the same check wherever else the program writes in bulk: freeze, adding to the master, building previews. Each knows its own byte total, so each is now a single call to the shared check.
  • Say how full every drive is, at start-up SHIPPED (2026-08-19) — the counterpart to the check above, and the cheaper half. Rather than only refusing a copy at the moment it would fail, the program now states the situation once, unprompted, when it starts: one line per volume with its size, its free space and the free percentage. On BigBoy that is five drives plus whatever card happens to be in the reader. Below ten per cent free reads as a warning, below five per cent as an alarm. It answers the question before it is asked, and unlike the pre-flight check it is visible on a day when nothing is going wrong yet — which is exactly when a drive filling up is still cheap to deal with.

    Network drives are deliberately left out: asking a disconnected share how big it is can take seconds, and nothing on the start-up path may wait that long. Empty card-reader slots are skipped for a related reason — asking them at all can raise Windows' own “there is no disk in the drive” box, which is silenced across the sweep. The whole report runs off to one side while the program carries on starting, so a drive that has spun down delays nothing.

    One thing turned up while building it: the log panel had no colour for errors at all. Warnings were tinted, and two specific phrases were painted red, but an error printed in exactly the same ink as a routine line — which is the failure this panel exists to prevent. Errors are now red everywhere in the program, not just here.
  • Reserve room on the card for its own ingest cache SHIPPED (2026-08-19) — SpeciesViewer keeps a small state file on the card itself (.sv_ingest_cache.json, in the folder being read) holding each file's checksum and capture date. It is what makes a second Read of the same card fast, and it travels with the card, which is the point: read a card on the laptop and later on BigBoy and both know what was already imported. It is small — a few hundred kilobytes for a couple of thousand files — but it is saved by writing a temporary copy first and then renaming, so a save briefly needs room for two of them. On a card with nothing left the write fails, and the failure was swallowed deliberately, because the same code must tolerate a write-protected card. Nothing was lost; the card simply re-hashed itself from scratch every time, which is exactly the kind of slow annoyance one does not want in the field.

    Is it worth guarding at all? Arithmetic first, because it decided the answer. Pictures are about 18 MB, so the space left over on a card shot to the end is essentially a random amount between nothing and one picture — under a megabyte roughly one card in eighteen. Per card that is negligible. Across the ten or so cards a long trip fills it is about a coin flip, and it lands on the evening you least want to spend twenty minutes re-hashing.

    What was built. A one-megabyte dummy file lives on the card, and it is deleted only after a save has actually failed: try to save, fail, spend the reserve, try once more, put the reserve back. The ordering is the entire design. The obvious alternative — delete the dummy before every write and restore it afterwards — would have SpeciesViewer deleting a file on the card on every single read, and the card holds the only original copy of the pictures. That is the same class of action that has actually cost data here before. This way the destructive step exists only on the one path where it is what saves you; on every ordinary read nothing on the card is touched.

    The reserve is laid down at the start of a read, which is when the card is most likely to still have room. On a good day a card can go from empty to full, and it typically gets read more than once along the way: the lunchtime read leaves the reserve while the card is half empty, and the evening read spends it.

    The other idea considered was to pad the cache file itself to its maximum expected size so it never has to grow. It does not survive contact with how the file is saved: the temporary copy means two copies exist at once regardless, so padding to maximum needs twice the maximum — worse, not better. It only helps if the atomic save is abandoned as well, and then an interrupted write leaves a corrupt cache. Survivable, since it is only a cache, but it trades a certain small cost for an occasional total one.

    The swallowed failure is now a visible one-line warning, but only when the card proved itself writable by giving the reserve up. A write-protected card stays as quiet as it always was, which is the normal condition the original silence existed for — no guesswork or error-code sniffing was needed to tell the two apart.

    One honest caveat on the testing: every branch was proven, but the full-card branch was proven by making the save fail on purpose, not by filling a real card to within a megabyte. The behaviour is right; the first genuine encounter will still be in the field.

    STILL OPEN the dummy has a name no scan can mistake for a picture, but nothing yet removes it on request — a card handed to somebody else still carries it. And the laptop-side fallback for a card that can never be written (a cache keyed by card fingerprint, the way the destination hash cache already works) remains unbuilt; it loses the travelling property, which is why it is a fallback and not the design.
  • Back up the day's work to a spare card — one ZIP per day OPEN / NEW — the cards keep the pictures safe, so this is not a picture backup: it is a backup of the work. A fortnight of culling, identification, locations and blog text lives on a single laptop, and re-doing it is a fortnight of evenings nobody gets back. There are two very large spare cards to write it to.

    Shape: one ZIP per day, written to a chosen removable card, holding that day's metadata (the XMP sidecars, any .dop, the day's CSVs and its blog text) and the pictures worth keeping — green and better, which is what the culling already decided. Per-day is the right grain: a day unchanged since the last run is skipped entirely, so a nightly backup costs only what was actually worked on. It pairs with the existing trip export, which already ships the trip's identity, species collection, lifer baseline and translation cache in kilobytes — the two together are a real restore rather than a pile of files.

    Of everything in this chapter this is the item that best fits the rule above: it reads the trip and writes a ZIP somewhere else, and nothing in the pipeline calls it, waits for it or breaks when it is skipped. Which also means the simplest possible version — every changed day, metadata only, no cleverness about what changed — is worth having on its own, before any of the refinements below.

    Decisions to make first: (a) one level or two — a metadata-only backup is tiny enough to run every evening without thinking, while metadata-plus-pictures is the one that survives a stolen laptop; (b) whether “green and better” means the RAW, the derived JPG, or whichever exists; (c) how a day is judged unchanged (a stamp per day, the way the upload cache already avoids re-sending files); (d) that the ZIPs should be stored rather than compressed — RAWs and JPGs do not shrink, so compression only costs time. And one rule to write into the design: the restore direction gets tested before the trip, not after it, because a backup nobody has restored from is a belief rather than a backup.
  • “Undo last delete” still has no button OPEN — the machinery exists and works: a delete moves files to a trash folder with a manifest, and a single call puts them back. Nothing in the interface calls it. Bulk delete by colour is precisely the evening job in a hotel room after a long day, and it is the one action with no way back from the keyboard.
  • The log is erased at every start, and lands wherever the program was launched from OPEN — studio.log is opened in “write” mode under a plain relative name, so every start throws away the previous session and the file's location depends on how the program happened to be started. Something odd happens on Tuesday, the program is restarted, and by Wednesday there is nothing left to look at — which matters far more when there is no second machine to reproduce it on. Give it an absolute location beside the other application data, and keep the last handful of sessions instead of one.
  • Rehearse the whole trip once, on the laptop, before leaving NEEDS TEST — several paths a trip depends on are built but have never been used in anger. Create Trip and Select or Update Trip were split into two one-directional dialogs after Create Trip overwrote a live trip's identity, and both have been verified to open but not driven end to end. Trip and Album overview parity has not been exercised live. The virtual-trip preview path is import-verified only. And the trip export / import round trip — the thing that eventually carries the trip home — has never been run in both directions. One evening covers it: create a trip, read a card into it, cull a day, write a blog, publish it, export it, import it back. Cheaper than any single feature on this list, and it is how the remaining surprises get found.
  • Show how old the SmallMaster snapshot is OPEN — on the road, whether a species is a lifer and which names get suggested both depend on the master snapshot carried on the laptop. Nothing shows when that snapshot was taken, so a stale one gives quietly wrong verdicts with no visible symptom. A date on screen is enough; refreshing it before departure belongs on the checklist below.
  • “Did this card arrive complete?” OPEN lower priority — every copied file is already checksummed at the destination and a mismatch already raises, so the program knows whether a card arrived intact; it just never says so. One closing line — all N files from this card are verified present — turns that into something a person can rely on. Lower priority than it first looked: with the cards kept as the original copy for the whole trip, nothing irreversible hangs on the answer.

Checklist before departure

Not work items — the things to do in the week before, once the above have been decided: refresh the SmallMaster snapshot and confirm its date shows; rehearse the round trip described above; confirm the backup card is formatted and that its restore direction has actually been tried; check free space against the trip's expected volume; and confirm the camera's clock and time zone match where you are going — the Read dialog now warns, but knowing beforehand is better.
